M1 – Provider-neutral transaction model: Purchase, subscription, seat grant, scholarship/manual grant, refund, chargeback and expiry are represented independently of provider-specific payloads.

M2 – Payment adapter and idempotency: At least one sandbox/mock provider drives the internal transaction flow, and duplicate/delayed/reordered webhook events cannot duplicate money-state or access-state changes.

M3 – Entitlement ledger: Current access to products/courses/features is derived from auditable ledger history rather than manually toggled application flags.

M4 – Commercial rules: Coupons/promotion rules, enterprise seat allocation/reassignment and subscription lifecycle are supported with clear conflict and expiry semantics.

M5 – Usage quotas: AI-intensive or premium features can enforce per-user or pooled usage limits safely under concurrent requests.

M6 – Refund and reconciliation: The system detects disagreement between provider-side payment state and internal ledger/entitlement state and safely repairs or escalates discrepancies.

M7 – Agent-mediated purchase adapter: A sandbox flow can propose a purchase, require explicit user authorization, preserve the approved item/merchant/amount and reject tampered, replayed, expired or cancelled authorizations.

M8 – Audit and failure validation: The complete transaction-to-entitlement history is inspectable, and injected network/provider failures converge to a correct state.

Done when: A sandbox demonstration completes one-time, subscription and enterprise-seat flows, correctly changes access after refund/expiry, reconciles deliberately lost/duplicate events and demonstrates an optional agent-authorized purchase without coupling the core ledger to the agent-payment protocol.

M1 - Transaction model (2026-08-12)
  - Ledger events: PURCHASE, SUBSCRIPTION_STARTED/RENEWED/CANCELLED,
    MANUAL_GRANT/REVOKE, CHARGEBACK, REFUND, SEAT_ASSIGNED/UNASSIGNED.
    Each has a source (payment/admin/scholarship/org seat), actor and reason.
  - Refund/chargeback/revoke must point at the event it undoes; only one
    reversal per event (checked in code AND in the database).
  - Free grants can't be refunded. A refund covers the whole order and asks
    the provider for the amount actually paid (after coupons).
  - Coupon discount is split across order lines, so ledger amounts add up.
  - Subscriptions are stacked paid periods. Since 2026-11-20 Refund refunds the
    whole current pass (every paid period still running or queued, one provider
    refund each) and then ends its free periods; Cancel renewal refunds only a
    renewal paid in advance. A REVOKE still removes just the period it names.
  - Refunds are webhook-driven: access is removed only when the provider's
    refund webhook arrives. A later refund.failed marks the order
    REFUND_FAILED for admin review.
  - UI: refund only on paid access, "Refund pending", Revoked / Charged back /
    Expired badges, admin grant form with source + reason.

M2 - Webhook retries and idempotency
  - Every webhook is saved in webhook_inbox first, then processed.
  - Failed rows are retried in the background: 30s, 60s, 120s ... up to 1h,
    marked DEAD after 8 tries. Admin can retry a row by hand.
  - A webhook that arrives too early (refund before its purchase) answers
    HTTP 503 so the provider sends it again.
  - Two deliveries of the same event at once are processed only once.

M3 - Entitlement ledger
  - Access is calculated from the append-only ledger (rebuilt at startup);
    the database blocks UPDATE / DELETE / TRUNCATE on the ledger.

M4 - Commercial rules
  - Coupons and pricing rules; one coupon per order; coupon is remembered
    across page reloads (cookie).
  - Enterprise seats: organizations + seat packs (N seats of one course).
    Assign / unassign / reassign by email; seats in use are counted from the
    ledger; two people can't take the last seat at the same time.
    Refunding a pack removes all its seats.
  - Subscription Renew (stacked after current end) and Cancel renewal
    (access kept until the end date).
  - Conflict rules written in README ("Commercial rules").
